# Ключевые архитектурные решения (ADR)

**Оркестрация (State Machine):** Выбран LangGraph.

**LLM (Core):** DeepSeek-V3 (через API). Оптимальное соотношение «цена/качество» для сложных задач классификации и генерации структурированных планов.

**Многоуровневая защита:** Вынос логики безопасности в отдельный входной узел (Security Node), работающий до активации основного роутера.

**Память:** MemorySaver (In-memory) для PoC. Постоянной и важной информации о пользователе не хранится, так что достаточно просто истории диалога в сессии.

**Tools:** Несколько тулов для парсинга резюме и вакансий, отбор вакансий, рекомендация и семантический поиск вакансий.

---

# Список модулей и их роли

| Модуль                 | Описание роли                                                                                  |
|------------------------|------------------------------------------------------------------------------------------------|
| Security Node          | Семантический фильтр. Классифицирует запросы на «Safe», «Out-of-Scope» или «Jailbreak».        |
| Main Agent (Router)    | Диспетчер системы. Принимает решение о следующем шаге на основе AgentState.                    |
| User Profile Agent     | Извлекает данные из ссылок HH.ru или текста, формирует JSON-профиль кандидата.                 |
| Vacancy Agent          | Выполняет RAG-поиск, делает Gap-анализ и строит план развития (Roadmap).                      |
| LLM-Judge              | Независимый модуль оценки качества и безопасности (Evals).                                    |

---

# Основной Workflow выполнения задачи

1. **Entry Point:** Запрос пользователя поступает в Security Node.
2. **Validation:** Если запрос признан опасным или нецелевым — система возвращает вежливый отказ и переходит в END.
3. **Routing:** Main Agent анализирует ввод. Если обнаружена ссылка при отсутствии профиля — переход в User Profile Agent.
4. **Processing:** Агент-обработчик обновляет данные в AgentState.
5. **Retrieval:** Если запрос требует подбора вакансий — управление передается в Vacancy Agent.
6. **Response:** Результат записывается в историю сообщений, и граф завершает работу.

# State / Memory / Context Handling

**State Definition:** Используется `TypedDict`, включающий `messages` (история), `user_profile` (структурированные данные), `scenario` (текущий интент) и технические флаги.

**Persistence:** Реализована через `MemorySaver` (краткосрочная, RAM) или `AsyncSqliteSaver` (долгосрочная, БД). Состояние восстанавливается по `thread_id`.

# Описание Retrieval-контура (RAG)

- **Хранилище:** Локальный векторный индекс FAISS.
- **Эмбеддинги:** `sentence-bert`.

**Алгоритм:**

1. Профиль кандидата конвертируется в вектор запроса.
2. Выполняется поиск по индексу FAISS.
3. LLM проводит финальное ранжирование (reranking) для выбора топ-10 наиболее подходящих вакансий.

# Tool / API-интеграции

- **DeepSeek API:** Генерация текстов и принятие решений.
- **HH.ru Parser Vacancy:** Извлечение вакансий и составление базы данных.
- **HH.ru Parser Resume:** Извлечение резюме по прямой ссылке.
- **title vacancy data:** Извлекает вакансии по title пользователя из резюме.
- **Recommender:** Рекомендация вакансий.

# Failure Modes, Fallback и Guardrails

- **Guardrail (Input):** Семантическая проверка в Security Node защищает от попыток подмены инструкций.
- **Failure Mode (Parsing Error):** Если парсинг ссылки не удался, система запрашивает у пользователя текстовую копию резюме.
- **Fallback (Search):** Если база вакансий не выдает релевантных результатов, система переходит в режим экспертных карьерных советов общего характера.
- **Guardrail (Output):** Модуль LLM-Judge мониторит ответы на предмет галлюцинаций и утечки системных данных.

# Технические и операционные ограничения

**Latency (Задержка):**
- Проверка безопасности: ~1–1.5 сек.
- Полный цикл генерации ответа: 120–150 сек. (p95).

**Cost (Стоимость):**
- Средняя стоимость обработки одного запроса: $0.03 – $0.05.

**Reliability (Надежность):**
- Зависимость от аптайма API DeepSeek.
- Точность извлечения данных из резюме: ~92%.
